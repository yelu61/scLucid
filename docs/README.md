# scLucid Documentation Map

This directory contains design, governance, and development documents for
scLucid. User-facing MkDocs documentation lives under `docs/`, with the main
navigation in `mkdocs.yml`.

## Current Implementation Snapshot

The core workflow is now documented around reviewable contracts rather than
only around function lists:

- **QC** writes `qc_reviewer_table`, threshold decision evidence, output health,
  and downstream preprocessing recommendations under
  `adata.uns["sclucid"]["qc"]["review_summary"]`.
- **Preprocess** writes `normalization_decision_policy`,
  `preprocess_layer_contract`, `preprocess_decision_summary`, and
  `preprocess_reviewer_table`. The stable layer contract is
  `counts -> normalized -> raw -> HVG -> scaled -> PCA -> graph`.
- **Analysis** writes `analysis_inference_policy`, `analysis_output_contract`,
  `analysis_decision_summary`, and `analysis_reviewer_table`. Condition DE is
  directed to sample-level pseudobulk; cell-level comparisons are labelled
  exploratory.

The root `README.md` should stay stable and describe only scLucid's identity,
core differentiators, quickstart, and documentation entrypoints. Implementation
details, field names, design notes, plans, and roadmaps should be tracked here,
in `docs/api/*.md`, `docs/user/best_practices.md`, and `docs/roadmap/`.
Archived design notes are provenance only and do not need routine updates.

For the current source-of-truth hierarchy, module feature map, stage plan, and
cleanup rules, read:

- `CURRENT_IMPLEMENTATION_AND_DOCS_POLICY.md`
- `user/module_features_and_plan.md`

### Developer Reference

The `docs/dev/` directory is maintained by developers to track the public API
surface and core workflow coverage. These files can become stale after
implementation rounds; verify gap items against code, tests, and API docs:

| File | Purpose |
|------|---------|
| `dev/FUNCTION_INVENTORY.md` | Auto-generated inventory of all public symbols in scLucid. |
| `dev/CORE_WORKFLOW_COVERAGE_MATRIX.md` | Manually curated mapping of core workflow stages to functions and gaps. |
| `dev/API_TRIAGE.md` | Staging area for uncertain, deprecated, or private-but-exposed APIs. |

`docs/dev/` and `docs/roadmap/` are complementary:

- `docs/roadmap/` is phase-oriented and submission-oriented. It answers what
  evidence, case studies, and release assets the project is trying to build.
- `docs/dev/` is engineering-oriented. It answers what public APIs, workflow
  coverage, compatibility aliases, and implementation gaps need code-level
  attention.

Both directories can contain time-sensitive material. Roadmap files should be
reviewed when phase priorities change; developer audits should be reviewed when
the relevant code or public API changes.

## Archive

Older design drafts and marker curation batches are kept under `docs/archive/`
for provenance. They are not the current implementation plan.
Archive files should not receive routine updates except to fix broken pointers
that confuse readers about the current source of truth.

| Archive Path | Contents |
|--------------|----------|
| `docs/archive/design_notes/` | Early strategy, QC, analysis, bulk/spatial, and feature-audit design notes superseded by current docs. |
| `docs/archive/marker_curation/` | Batch marker curation notes and historical coverage summaries. |
| `docs/archive/sphinx_source_legacy/` | Legacy Sphinx source retained as a temporary fallback after MkDocs migration. |

When adding new planning documentation, update either the strategic plan above
or the phase playbook below instead of creating another parallel roadmap.

## Phase Playbook

The `docs/roadmap/` directory expands the strategy into execution phases for
implementation and submission readiness:

- Phase 1: Core API and evidence contracts.
- Phase 2: QC evidence benchmark.
- Phase 3: Preprocess and analysis validation.
- Phase 4: Tumor interpretation case studies.
- Phase 5: Tumor ecosystem modeling.
- Phase 6: Knowledge and evidence infrastructure.
- Phase 7: Support evidence modules and R/Python parity.
- Phase 8: Release, manuscript, and submission package.
